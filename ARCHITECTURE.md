# hostd architecture

Milestone 1 is a Go modular monolith. `hostd` owns a local SQLite control-plane database and an HTTP API bound to loopback by default. The daemon creates the local machine record, serves embedded dashboard assets, and uses durable database jobs for all application mutations. A fake runtime is available only when explicitly configured for development or tests; it never invokes Docker or a shell.

HTTP handlers are deliberately thin. They validate/authenticate requests, delegate to the `apps`, `auth`, `jobs`, and `machines` services, then serialize stable JSON or RFC 9457 problem responses. Browser mutation routes require a session cookie and matching CSRF header. Opaque session and bootstrap tokens are stored only as SHA-256 hashes; passphrases use Argon2id. While bootstrap is pending, its plaintext exists only in an atomic protected file under the data root: owner-only `0600` on POSIX, current-user DPAPI ciphertext on Windows. Startup emits only that file path; `hostctl bootstrap-token --file` is the explicit retrieval route. The file is removed after successful bootstrap, expiration, and clean shutdown.

`jobs` serializes mutating work per application through a database uniqueness constraint. Jobs and their ordered append-only events survive daemon restarts. On startup, jobs that were assigned/running/waiting are explicitly interrupted and retain their checkpoint for later recovery. SSE reads persisted events first and then waits for new events; it can resume after `Last-Event-ID`.

The dashboard is a Vite React SPA compiled into `web/dist` and embedded via `go:embed`. A server fallback serves `index.html` for non-API deep links. The API source of truth is `api/openapi.yaml`; the repository-owned `cmd/openapi-gen` tool deterministically derives Go and TypeScript operation/schema-name artifacts. The HTTP router and browser client consume those artifacts, and generation checks fail on source drift.

Docker and Compose diagnostics execute only the resolved Docker client with fixed argument arrays, scoped environment values, and bounded contexts. Host memory/disk values and discovered runtime versions are persisted into the local machine record. CLI sessions are read from protected JSON files or standard input; login credentials are accepted only over standard input and never through process arguments.

GitHub source connections use the official GitHub App device flow with fixed `github.com` and `api.github.com` origins and no client secret. SQLite stores only owner-scoped lifecycle, provider identity, expiry, generation, safe error-code, and installation display-cache metadata. Device codes, one-shot token exchanges, and rotating access/refresh bundles are stored in separate connection-purpose-bound protected files. Per-connection locks serialize polling, promotion, refresh, live provider access, and local disconnect; bundle generations reconcile a successful protected-file write that precedes a failed database update. Local disconnect destroys protected credentials before clearing the display cache and metadata. Installation cache rows are non-authoritative: repository and branch discovery always use the authenticated user's live provider token and revalidate the immutable repository ID within the selected installation.

Every application has exactly one typed `local` or `github` source row. Existing applications are backfilled as local and continue to use `applications.source_path`; GitHub rows retain only credential-free immutable repository identity, refreshed display names, the tracked branch/ref, selected Compose path, and last inspection SHA. GitHub inspection resolves a branch once, rejects truncated or unsafe trees, and fetches only the selected bounded Compose document. Local inspection walks a bounded source tree without following links. Both paths return service names and source-structure findings; effective Compose runtime policy and elevated-capability approval are separate deployment-runtime concerns.

GitHub release materialization resolves the tracked branch once through the owner-scoped connection, rejects truncated trees and submodules, then downloads the resolved commit archive through the authenticated GitHub API. Only a single canonical codeload redirect is followed and never carries an Authorization header. The compressed archive is bounded and hashed before a strict single-root tar extraction. Workspaces live only under the controller data root, and release records retain credential-free provenance, compressed archive hash, a data-root-relative workspace reference, and materialization state. Staging and final paths are generated from validated IDs; interrupted rows are marked failed at startup after only their managed paths are removed. A ready workspace is revalidated before reuse.

Application configuration revision 0 is a virtual empty head with no file. Every later revision is an immutable, application-and-revision-purpose-bound protected bundle under the managed data root; SQLite retains only revision identity, key sensitivity metadata, counts, and bundle references. Replacement writes and syncs the new file before a compare-and-swap database transaction, and startup validates every reference while deleting only exact recognized crash orphans. APIs return visible variable values but omit secret values entirely. Each materialized release pins the application configuration revision current in its reservation transaction and never rewrites that provenance. A prior release deployment records whether it used that original revision or the application's current revision.

The production Docker Compose executor is opt-in and controller-local. It renders effective configuration with fixed argument arrays and a scoped environment, evaluates that normalized model before mutation, and executes only a protected temporary Compose document and environment file. Workspace escapes and remote resources are rejected. Named volumes, managed-workspace build/bind paths, and loopback ports are allowed; elevated host access and non-loopback bindings require an exact stored approval fingerprint. Jobs wait for administrator attention before `compose up` when a new finding is unapproved. Health failures and partial applies preserve diagnostics, release workspaces, and existing containers; Rig never claims or performs automatic rollback.

The official webhook relay is a separately deployable Go service whose authoritative state is PostgreSQL. It verifies GitHub webhook HMACs over exact raw bodies, deduplicates delivery IDs, persists a monotonically versioned desired state before success, and recovers failed GitHub deliveries. Enrollment uses a short-lived GitHub web OAuth/PKCE authorization to verify the user, installation, and repository relationship, then discards the user token. Relay storage and telemetry exclude source/configuration payloads, application names, user tokens, and raw webhook bodies.

Controllers use a separate protected Ed25519 identity and make outbound-only authenticated WSS connections. Protocol transcripts bind the version, controller/key/session identities, nonces, and acknowledgement state. A desired-source envelope is acknowledged only after it is durable in local SQLite. The auto-deploy coordinator then resolves the tracked branch's current head with the controller's GitHub credential, coalesces intermediate pushes, and schedules at most one follow-up after an active deployment. Failure, missing configuration, access loss, or a new approval requirement pauses automatic deployment without disabling manual deployment.

The embedded dashboard composes these boundaries rather than bypassing them: GitHub source selection, versioned configuration, deployment/release history, exact approvals, prior-release recovery, per-app auto-deploy, and relay enrollment/binding/key management all call authenticated controller APIs. Relay enrollment authorization URLs are accepted only when their GitHub origin and complete OAuth/PKCE query bind to trusted controller/request state.
